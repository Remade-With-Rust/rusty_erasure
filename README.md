# rusty_erasure

Intel [ISA-L](https://github.com/intel/isa-l)'s erasure coding, remade with Rust: a
matrix-flexible GF(2^8) Reed-Solomon engine — encode, incremental update, and first-class
recovery — with a `no_std`, zero-dependency, `forbid(unsafe)` core, validated parameters
(ISA-L validates nothing), and SIMD acceleration behind runtime dispatch. No C, no NASM,
no GPL, anywhere in the build. MIT OR Apache-2.0.

Part of the [Remade-With-Rust](https://github.com/remade-with-rust) family. The erasure
primitive under SpaceDB/disco shard placement: k+p shards across peers survive p losses at
(k+p)/k overhead instead of 3× replication.

**Status: 0.1.0, feature-complete and conformant; pre-publish.** The mission plan — scope,
architecture, conformance oracle, and release gates — is
[docs/plans/erasure_mission.md](docs/plans/erasure_mission.md). Every claim below has an
entry in [corpus/LEDGER.md](corpus/LEDGER.md) with the run that produced it; nothing is
claimed that is not ledgered.

## Conformance

**Byte identity** with ISA-L's `erasure_code` module, proven — not asserted — against
golden vectors generated from real ISA-L v2.32.1:

- **902/902** full-grid cases (every Cauchy k=1..32 × p=1..8 at three lengths, plus every
  safe-region Vandermonde config), replayed through the shipping dispatched path
- **65,536/65,536** GF(2^8) products and **256/256** inverses against ISA-L's own tables
- **1470/1470** exhaustive loss patterns recovered on (10,4), gated on ground truth
- **3/3** bidirectional compatibility with the real `reed-solomon-erasure` crate — its
  shards decode here and ours decode there
- Every SIMD kernel byte-identical to the `forbid(unsafe_code)` scalar oracle, on x86-64
  (SSSE3 / AVX2 / AVX2-GFNI), aarch64 NEON, and wasm SIMD128 — the last two executed in CI
  under qemu and wasmtime
- Miri (31 tests, zero UB), ASan fuzzing (~5.7M execs, zero open crashers)

## Performance

Measured against **ISA-L's own dispatched `avx2_gfni` assembly** on the same silicon,
interleaved ABBA, pinned, on process CPU time, with work identity gated by parity
checksums. Source-bytes basis, best-of-3. Ratios above 1.00 mean this crate is faster:

| Cell | rusty_erasure | ISA-L | Ratio |
|---|--:|--:|--:|
| S1 (4,2) 4 KiB | 59.35 GB/s | 54.46 | **1.09×** |
| S2 (10,4) 64 KiB | 25.27 GB/s | 19.02 | **1.33×** |
| S3 (10,4) 1 MiB | 21.65 GB/s | 13.22 | **1.64×** |
| S5a (17,3) 64 KiB | 30.34 GB/s | 28.74 | **1.06×** |
| S5b (20,8) 64 KiB | 10.40 GB/s | 10.51 | 0.99× |
| RAID xor (10) 64 KiB | 89.48 GB/s | 86.60 | **1.03×** |
| RAID pq (10) 64 KiB | 65.37 GB/s | 64.01 | **1.02×** |
| Recover e=1 (10,4) 64 KiB | 64.86 GB/s | 53.11 | **1.22×** |
| Recover e=2 (10,4) 64 KiB | 45.10 GB/s | 35.92 | **1.26×** |

Multi-stripe: **130 GB/s** aggregate across 24 threads (wall basis). The recovery arms are
measured with ISA-L's matrix work amortized *outside* its loop and ours *inside* — the
handicap is ours. Full method lines, the cells where the picture is closer, and every
reverted experiment are in the ledger.

## Workspace

| `rusty_erasure-alloc` | The rusty_alloc seam — one crate, one pin. |
| `rusty_erasure-demo` | The browser demo: erasure coding in wasm, no server. |

## Security

No network, no filesystem, no secrets — pure computation over caller buffers. Parameters
are validated and every misuse is a typed error, never a panic (ISA-L validates nothing).
Erasure parity is **not** a MAC: sign or authenticate shards separately if you need
integrity against an adversary rather than against loss. See
[SECURITY.md](SECURITY.md).
